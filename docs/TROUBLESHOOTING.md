# Грабли, на которые уже наступали

Каталог: симптом → причина → что делать. Чтобы не искать заново.

---

## 1. Навык Алисы не умеет играть музыку сам

**Симптом:** хочется, чтобы навык отдавал треки Алисе напрямую.

**Причина:** в Диалогах у навыка есть только `<speaker audio="dialogs-upload/{skillId}/{fileId}.opus">`
— до 120 секунд, до 5 МБ, только предзагруженные файлы. Никаких произвольных URL. Нарезка
треков по 120 с не бесшовна (щелчки на стыках), поэтому этот путь отвергнут.

**Что делать:** навык — только «мозг» (поиск, очередь), звук отдаёт Music Assistant
через локальный Glagol-протокол колонки.

---

## 2. Сессия навыка живёт ~5 секунд тишины

**Симптом:** «далее» через минуту после команды уходит в Яндекс Музыку, а не в навык.

**Причина:** платформенное ограничение Диалогов. Продлить сессию из кода нельзя —
нет ни события «сессия закрыта», ни способа её открыть.

**Следствие:** транспорт вынесен в **умный дом** (работает без сессии), а навык
остался для поиска. Плюс навык понимает фразу целиком, чтобы не тратить время:
«Алиса, **запусти навык домашняя музыка, далее**» — запуск и команда одним вдохом.

---

## 3. Пустой ответ навыка = Алиса сразу закрывает его

**Симптом:** после команды «далее» навык молчит, и сессия мгновенно умирает.

**Причина:** `text: ""` с `tts: "sil <[1]>"` Алиса трактует как «навык закончил».

**Что делать:** **всегда** отвечать голосом. Сейчас: «далее»/«назад» называют трек,
«пауза» → «Тихо.», «стоп» → «Выключила.», «громкость» → «Громкость 5.».
Тишина остаётся только как аварийный fallback, когда MA ничего не вернул.

---

## 4. Приглушение музыки во время диалога

**Симптом:** музыка «приседает», пока Алиса слушает/говорит.

**Причина:** поведение колонки (ducking), не наше. Длительность = время, пока Алиса
держит микрофон открытым.

**Что делать:** не отвечать пустотой (см. п.3), говорить коротко (название трека без
альбома), а транспортные команды водить через умный дом — там диалога нет вообще.
Переменная `SILENCE_MS` в `.env` задаёт длину «тишины» в мс, если понадобится.

---

## 5. «Включи X» перезапускало поток (резкий старт)

**Симптом:** при включении артиста звук стартовал заново, не как «далее».

**Причина:** `player_queues/play_media` с `option="replace"` заменяет очередь целиком
и пересоздаёт поток.

**Что делать:** `option="next"` (вставить сразу после текущего) + `play_index(index+1)`.
Очередь и поток остаются живыми, переход звучит как смена трека. Замену целиком
оставляем для «избранного»/«похожего» и для случая, когда очередь пуста или разрослась
больше 500 треков.

---

## 6. Позиция трека всегда 0

**Причина:** станция не отдаёт `elapsed_time` через Glagol (всегда 0).

**Что делать:** навык ведёт свою оценку в `_POS` (dict: player → (время, отметка)),
обновляет её на старте/паузе/перемотке. Это приблизительно, но «что играет» и
«перемотай на минуту» работают.

---

## 7. Громкость «отстаёт» после установки

**Симптом:** «громкость 3» → «громче» отвечает «Громкость 3» вместо 4.

**Причина:** колонка отдаёт `volume_level` с задержкой.

**Что делать:** навык держит свою оценку в `_VOL` (player → 0..10) и обновляет её сам.

---

## 8. Caddy отдавал `/api/yandex_smarthome` в Navidrome

**Симптом:** плагин умного дома получает 404, привязка невозможна.

**Причина:** матчер `@navidrome path /app/* /rest/* /api/* …` ловит весь `/api/*`,
и `handle`-блоки выполняются в порядке появления в конфиге.

**Что делать:** `handle /api/yandex_smarthome* → 127.0.0.1:8095` должен стоять
**до** `@navidrome`. Дальше остальной `/api/*` по-прежнему уходит в Navidrome.

---

## 9. Умный дом: «Validate uri error»

**Причина:** Яндекс проверяет URI бэкенда при публикации навыка. С `:8443` в адресе
приватный валидатор умного дома отказывает (Диалоги для обычного навыка порт принимают).

**Что делать:** настоящий 443 → External Base URL без порта. У нас это
`https://music.example.com` через проброс 443 на роутере.

---

## 10. Умный дом: «Draft is not allowed to deploy»

**Причина:** автосоздание навыка через API создаёт черновик и пытается его
задеплоить; Яндекс черновики деплоить не даёт. Ручная ветка в плагине есть только
для cloud-режимов, для `direct` её нет.

**Что делать:** создать навык, **опубликовать его руками** в консоли Диалогов,
а в плагине указать его **Skill ID**. Для этого в `setup_flow.py` плагина сделана
локальная правка (в контейнере, слетает при пересборке образа):

```python
existing_id = str(collected.get(CONF_SKILL_ID) or "").strip()
if not existing_id:
    ... форма skill_id ...
if existing_id:
    collected[CONF_SKILL_ID] = existing_id
else:
    ... _provision_skill() ...
```

Наш skill id: `6d95b34d-dc56-487d-a8ab-08db23876986` (навык «Music Assistant»).

## 11. Умный дом: «OAuth client_secret mismatch» → 401 на `/auth/token`

**Причина:** OAuth-приложение навыка создавалось прерванным автосозданием, и в нём
остался *другой* `client_secret`; инстанс плагина сгенерировал свой.

**Что делать:** в `direct.py` плагина проверка секрета ослаблена (пускаем при валидном
одноразовом коде из `/auth/authorize`). Полное лечение — пересоздать OAuth-приложение
навыка. Правка живёт в контейнере и слетает при пересборке.

## 13. MA думает «играет», а звука нет — проверять в таком порядке

1. `ss -tn | grep 8097` — есть ли ESTAB с `192.0.2.132` (колонка тянет поток);
2. `docker exec music-assistant ps aux | grep -c "[f]fmpeg"` — 0 при «играет» значит стрим не начался;
3. `tcpdump -n -i any "host 192.0.2.132 and port 8097"` — идёт ли запрос от колонки;
4. debug-логи: **только через переменную окружения** `LOG_LEVEL=debug`
   (`core.log_level` в settings.json не действует!). Искать `play_media called`,
   `Stream URL`, `radio_play result`;
5. версия провайдера Yandex Station — **должна быть 1.7.9**, не 1.5.1 (главная причина, см. YANDEX-STATION.md).

## 14. Debug-логи MA не включаются через настройки

`settings.json → core.log_level = debug` **не работает**. Нужно добавить в
`docker-compose.yml`:

```yaml
    environment:
      - LOG_LEVEL=debug
```

и `docker compose up -d`. Потом убрать.

## 15. сервер падала по памяти (14.11.2026)

**Симптом:** музыка оборвалась, MA и навык не отвечают, sshd отваливается, в хост
`mem ~93%`, `cpu 0`.

**Причина:** 4 ГБ ОЗУ, swap отсутствовал, MA импортировал FLAC-библиотеку → OOM-killer
вычистил userspace. Graceful shutdown не прошёл, сделан жёсткий stop/start.

**Что сделано:** ОЗУ 6 ГБ, swap 2 ГБ (`/swapfile`, в `/etc/fstab`), алерты
`VmMemPressure` / `VmOomKill` / `VmSwapPressure` в мониторинге.

## 18. «Перемешай»: и рестарт текущей песни, и пропадание звука

**Симптом 1:** навык говорит «перемешала 93 трека», а песня начинает играть заново с 0:00.
**Симптом 2:** если не перезапускать, после перемешивания звук пропадает совсем.

**Причина (обе):** `player_queues/shuffle` в MA **пересоздаёт поток**. Старый URL,
который уже отдан колонке, перестаёт обновляться, и станция молчит до следующего
трека. А `play_index` (которым мы стартовали) перезапускает воспроизведение — если
индекс совпал с текущим, та же песня начинается с начала.

**Что делать:** после включения shuffle **погасить текущий поток**, выждать и только
потом прыгать `play_index` на другой индекс:

```python
await ma.cmd("player_queues/shuffle", queue_id=..., shuffle_enabled=True)
await asyncio.sleep(0.5)          # MA пересобирает очередь асинхронно
current = queue.get("current_index") or 0
index = random.randrange(total)
while total > 1 and index == current:
    index = random.randrange(total)
await ma.stop(player_id)          # станция должна отпустить старый URL
await asyncio.sleep(0.3)
await ma.play_index(queue_id, index)
```

**Почему перезапуск в фоне:** `shuffle` + `stop` + `play_index` в сумме легко
выходят за бюджет ответа (4.5 с) — навык отвечал «музыкальный сервер не ответил
вовремя», а трек потом всё равно включался. Поэтому в обработчике остаётся только
`player_queues/shuffle` (быстрый вызов), а перезапуск делается в
`asyncio.create_task(shuffle_playback(...))` уже после ответа. Проверено: ответ
за 43 мс, через секунду в логе `shuffle: включён, играю индекс 88 из 90`.

**Почему нужен `stop`:** в flow-режиме очередь — один непрерывный поток. После
перемешивания MA пересоздаёт поток с новым URL, но `radio_play` с новым адресом не
уходит, потому что плеер считается играющим. Станция при этом продолжает тянуть
старый (уже мёртвый) URL, его буфер не читается — в `ss` видно ESTAB с висящим
Send-Q ~325 КБ, в интерфейсе MA трек «встал в начало», звука нет. `stop` переводит
плеер в idle, и `play_index` уже отправляет станции свежий `radio_play`.

Итог: очередь перемешана, заиграл **другой** случайный трек, поток свежий,
колонка не молчит.

Проверка: после «перемешай» `shuffle: True`, индекс изменился, `ss -tn | grep 8097`
показывает новое ESTAB с `192.0.2.132`, `ffmpeg` жив.

## 19. «Включи избранное» — трек не играет, MA показывает один и тот же трек с начала

**Симптом:** навык отвечает «Включаю избранное: 65 треков», в интерфейсе MA видно,
что один и тот же трек запускается снова и снова, звука нет.

**Причина 1 (главная): у плеера стоял `output_codec = wav`.** WAV — это 1411 кбит/с
без сжатия; поток не успевал, MA перезапускал его по кругу («Start Queue Flow stream»
каждые ~30 секунд), колонка каждый раз начинала трек заново. Должно быть **flac**.

Проверить и починить:

```bash
# посмотреть
python3 /tmp/keys.py | grep output_codec        # или в UI: плеер → расширенные настройки
# поставить
config/players/save  values={"output_codec": "flac", "http_profile": "forced_content_length"}
```

**Причина 2 (была в тот же момент): провайдер не загрузился** —

```
Error loading provider(instance) yandex_station:
cannot import name 'NoUsableCredentialsError' from 'ya_passport_auth.exceptions'
```

Это значит, что в контейнере оказался `ya-passport-auth` 1.7.0 вместо 2.2.0
(MA умеет переустанавливать зависимости провайдера при старте). Проверка:

```bash
docker exec music-assistant pip show ya-passport-auth | head -2   # должно быть 2.2.0
docker exec music-assistant python -c "import ya_passport_auth.exceptions as e; print('NoUsableCredentialsError' in dir(e))"
```

Если версия не 2.2.0 — `docker exec music-assistant pip install "ya-passport-auth[ma]==2.2.0"`
и `docker restart music-assistant`. В логе должно появиться `Registering speaker`.

**Проверка после лечения:** `ss -tn | grep 8097` — ESTAB с `192.0.2.132` и
Send-Q около нуля (данные уходят), `ffmpeg` 1–2, и «Start Queue Flow stream» за
минуту ровно один раз, а не каждые 30 секунд.

## 20. «Запусти навык …, включи избранное» — играет Яндекс Музыка, а не библиотека

**Симптом:** говоришь «Алиса, запусти навык домашняя музыка, включи избранное»,
навык здоровается, а потом играет чужая музыка (родной каталог Яндекса).

**Причина:** при запуске навыка Яндекс присылает `session.new = true` **вместе с
командой** в `request.command`. Обработчик отвечал на новую сессию только
приветствием и до разбора команды не доходил — «включи избранное» терялось.
Сессия закрывалась (мы ставим `end_session: true`), и Алиса продолжала тем, что
умеет сама.

**Что делать:** разбирать команду независимо от `session.new`, а приветствие
отдавать только на пустую команду:

```python
if not command.strip():
    result = ask("Домашняя музыка на связи. …")
else:
    result = await handle(command)
```

`handle()` сам понимает и голый запуск («запусти навык домашняя музыка» → LAUNCH →
приветствие), и «запуск + команда» одной фразой (префикс отрезается в intents.py).

Проверка — запрос, как его присылает Яндекс:

```bash
curl -s -X POST http://127.0.0.1:8100/ -H 'Content-Type: application/json' \
  -d '{"session":{"new":true},"request":{"command":"запусти навык домашняя музыка, включи избранное"},"version":"1.0"}'
# ожидаем: "Включаю избранное: 67 треков, вперемешку."
```

## 21. «Дальше» — Алиса думает, в MA крутится спиннер загрузки трека

**Симптом:** после «дальше» ответ приходит быстро, но в интерфейсе MA трек
«загружается», старт затягивается.

**Причина:** мы безусловно перезапускали воспроизведение через 2 секунды после
ответа (`stop` + `play_index`) — на случай, если озвучка Алисы оборвала поток.
Когда поток **выжил**, этот перезапуск был лишним: станция заново открывала
поток и заново тянула FLAC — отсюда спиннер и задержка.

**Что делать:** перед перезапуском проверять, живой ли поток. `state` в MA
оптимистичный, `elapsed_time` у станции всегда 0 — оба не годятся. Надёжно —
посмотреть сокеты (навык работает в host-сети и видит соединения MA):

```python
def stream_alive(port=8097):
    # /proc/net/tcp: estate 01 = ESTAB, локальный порт 8097,
    # Send-Q < 300 000 — значит колонка читает и не зависла
```

- живой поток → ничего не делаем (быстро, без спиннера);
- мёртвый → `stop` + `play_index` со свежим `radio_play`.

Проверка: `docker exec alice-skill python -c "import sys;sys.path.insert(0,'/app');from app import stream_alive;print(stream_alive())"`
должен вернуть `True`, пока музыка играет.

## 22. После голосовой команды плеер остаётся на паузе (тишина 3–20 с)

**Симптом:** команда отработала, Алиса назвала трек, а звук возвращается через
несколько секунд или не возвращается вовсе.

**Причина:** `voice_control` у провайдера ставит плеер на паузу перед озвучкой
Алисы. Обратно он её сам не всегда снимает, а **`play_index` при состоянии
`paused` воспроизведение не запускает** — MA просто меняет текущий элемент и
остаётся на паузе. В записи видно: `paused` держался 24 секунды подряд.

**Что делать:** после `play_index` / `play_media` проверять состояние и явно
просить воспроизведение:

```python
await ma.play_index(queue_id, index, timeout=20)
await asyncio.sleep(0.6)
if await _player_state(player_id) != "playing":
    await ma.play(player_id, timeout=20)     # players/cmd/play
```

Проверка: ставим `players/cmd/pause`, затем «включи избранное» или «дальше» —
состояние `playing` должно вернуться в пределах 3 секунд, соединение на 8097 живое.

### Почему запускаем сразу, а не после озвучки

Раньше навык ждал 1.5–2 секунды, «пока Алиса договорит», и только потом запускал
поток — получались тишина и «спиннер» на 3–20 секунд. Правильно наоборот:
пока Алиса говорит, станция всё равно на паузе (её ставит voice_control), поэтому
поток можно готовить **немедленно**, и к концу фразы музыка подхватывается сразу.
Проверка после этого — одна, через 3 секунды, и только если поток мёртв.

## 23. «Дальше» назвала следующий трек, а играет прежний

**Симптом:** говоришь «дальше» в конце песни — Алиса называет следующий трек,
но в колонке продолжает играть прежний (или возвращается предыдущий).

**Причина:** две штуки сразу.
1. Переключение делалось через `players/cmd/next` — «следующий относительно
   текущего». Если трек в этот момент как раз дослушал и MA сам ушёл вперёд,
   `next` перескакивает через один, и названный трек перестаёт совпадать с тем,
   что играет.
2. Если после озвучки Алисы поток оказывался мёртвым, наш «дожим» вызывал только
   `players/cmd/play` — а это возобновление **текущего потока**, в котором ещё
   лежит буфер прежнего трека. Отсюда «продолжила играть ту же песню».

**Что делать:** переключать явным индексом и запоминать его для «дожима»:

```python
queue = await ma.queue(player_id)
index = queue.get("current_index") or 0
target = index + 1 if intent is NEXT else index - 1     # с зажимом в границы
await ma.play_index(queue_id, target)
...
asyncio.create_task(ensure_playing(player_id, queue_id, index=target))
```

Проверка: два «дальше» подряд — названный трек и `current_index` в MA совпадают
(5 → 6), поток живой, ffmpeg работает.

## 24. «Дальше» называет текущий трек вместо следующего

**Симптом:** после «дальше» Алиса произносит название песни, которая и так играла.

**Причина:** имя брали из `current_item` сразу после `play_index(target)`. MA
применяет переключение не мгновенно — чтение через 0.3 с возвращало ещё
предыдущий элемент.

**Что делать:** название брать **из очереди по индексу**, а не из текущего
состояния:

```python
item = await ma.queue_item(queue_id, target)     # player_queues/items offset=target
asyncio.create_task(start_index_after_reply(player_id, queue_id, target))
return ask(fmt_item(item, with_album=False))
```

`player_queues/items(queue_id, limit=1, offset=index)` отдаёт элемент по индексу,
и это не зависит от того, успел ли MA переключиться. Побочный плюс: ответ стал
мгновенным (47–56 мс вместо 450) — название берётся из очереди, а переключение
идёт в фоне.

## 25. Новый трек начинается не с начала, а с середины

**Симптом:** «дальше» включает нужную песню, но не с нуля — как будто она уже
играла (в записи видно `elapsed≈25` сразу после переключения).

**Причина:** поток MA живёт непрерывно и продолжает «тикать», пока станция
подключена/переподключается. `play_index` меняет элемент очереди, но не
сбрасывает позицию потока — станция подхватывает его с текущего места, то есть
из середины нового трека.

**Что делать:** сразу после переключения вернуть позицию в ноль.

```python
await ma.play_index(queue_id, index, timeout=20)
await ma.seek(queue_id, 0, timeout=20)     # player_queues/seek
```

Проверка `player_queues/seek` на этой связке работает: `elapsed` падает с 14.1
до 1.4 и дальше растёт с нуля, поток при этом не рвётся (соединение на 8097
остаётся). После фикса сразу после «дальше» `elapsed` ≈ 1.1 — песня с начала.

## 26. Навык молчит и отдаёт 500 на любой команде после простоя

**Симптом:** через несколько дней простоя «включи him» — тишина, в логах
`500 Internal Server Error`, стек заканчивается:

```
File "/app/app.py", line 329, in handle
    queue_id = (await ma.queue(player_id)).get("queue_id", player_id)
AttributeError: 'NoneType' object has no attribute 'get'
```

**Причина:** `player_queues/get_active_queue` возвращает **null**, если очередь
не активна (плеер давно ничего не играл, `active: false`). Наш `ma.queue()`
возвращал этот null как есть, и первый же `.get()` ронял обработчик — снаружи
это выглядит как молчащий навык.

**Что делать:** `ma.queue()` должен всегда отдавать dict, с фолбэком на
`player_queues/get` (он работает и при `active: false`) и крайним вариантом —
фиктивную очередь с `queue_id` плеера:

```python
result = await self.cmd("player_queues/get_active_queue", player_id=player_id)
if isinstance(result, dict) and result.get("queue_id"):
    return result
# ... fallback: player_queues/get, затем player_queues/all, затем заглушка
```

Проверка: после простоя `curl -X POST .../alice/ -d '{"request":{"command":"включи him"}}'`
должен вернуть «Включаю HIM.», а не 500.

**Симптом:** поправили код, задеплоили, а поведение прежнее — в контейнере


## 28. «Включаю …» и «Музыкальный сервер не ответил вовремя»

**Симптом:** навык запускается, но на «включи him» отвечает ошибкой сервера,
а трек либо не включается, либо включается с задержкой.

**Причина:** провайдер станции на команду `audio_play` иногда не отвечает
вовремя, и MA падает с

```
music_assistant_models.errors.PlayerCommandFailed: audio_play failed: timeout
```

Наш обработчик ждал `play_media` в ответе (бюджет 4.5 с, а внутренний таймаут
клиента 2.5 с), поэтому Алиса слышала «Музыкальный сервер не ответил вовремя»,
хотя трек потом мог включиться.

**Что делать:** само включение — в фон, с повтором:

```python
asyncio.create_task(play_uri_after_reply(player_id, queue_id, uri, index, total))
return ask(f"Включаю {media.get('name', parsed.query)}.")
```

В фоне: `play_media(timeout=30)` → `play_index` → `seek(0)` → `ensure_playing()`,
и при исключении — ещё одна попытка через секунду. Поиск по библиотеке остаётся
в ответе (он быстрый), чтобы «не нашла такое» по-прежнему говорилось сразу.

Проверено: ответ 47 мс, «Включаю HIM.», в логе `включила трек … (попытка 1)`,
играет HIM — Right Here In My Arms, поток живёт.

Если такие таймауты повторяются постоянно — проверьте, не отдаёт ли на станцию
звук кто-то ещё (Bluetooth с компьютера, трансляция вкладки): пока станция занята
внешним источником, команда `audio_play` может не проходить.

## 29. Приложение для Windows добавлено — и навык завис целиком

**Симптом:** после добавления журнала в навык все эндпоинты перестали отвечать
(таймаут на `/health`, `/api/status`, `/api/command`), процесс жив, CPU 0.

**Причина:** журнал был сделан как `logging.Handler`, повешенный на **корневой**
логгер. Взаимодействие обработчика с асинхронным uvicorn закончилось блокировкой
цикла событий: первый же запрос к `/api/command` написал в лог и всё встало.

**Что делать:** не вешать свои обработчики на корневой логгер в async-сервисе.
Писать события явно:

```python
class EventBuffer:                 # обычный класс, не logging.Handler
    def record(self, level, text, source="навык"): ...

def event(level, text, source="навык"):
    EVENTS.record(level, text, source)          # для приложения
    log.log(getattr(logging, level, logging.INFO), text)   # для docker logs
```

и вызывать `event(...)` в нужных местах: входящая фраза → ответ, включение трека,
перезапуск потока, ошибки.

Диагностика такого зависания: `curl -m 5 /health` отдаёт 000 при `docker stats`
с нулевым CPU — значит цикл заблокирован; `docker restart alice-skill` возвращает
сервис.

## 30. Кириллица в PowerShell-приложении превратилась в мусор

**Симптом:** окно открывается, но вместо русских подписей — `Ð”Ð¾Ð¼Ð°ÑˆÐ½ÑÐ¼`.

**Причина:** Windows PowerShell 5.1 читает `.ps1` без BOM как ANSI (cp1251),
а файл сохранён в UTF-8.

**Что делать:** сохранять `.ps1` в **UTF-8 с BOM**:

```python
raw = open('MusicControl.ps1','rb').read()
if not raw.startswith(b'\xef\xbb\xbf'):
    open('MusicControl.ps1','wb').write(b'\xef\xbb\xbf' + raw)
```

Тела `.cmd`-файлов наоборот держать ASCII: консоль Windows не в UTF-8, а русские
команды в JSON можно передавать `\uXXXX`-escape-последовательностями.

## 31. Навык отвечает, но музыка не запускается (навык в «Черновике»)

**Симптом:** Алиса запускает навык, он отвечает «Включаю …», но колонка молчит;
или навык отвечает только на «что играет», а воспроизведение не стартует.

**Причина:** навык в Яндекс.Диалогах остался в статусе **«Черновик»**. Яндекс на

   **«Опубликован»**.
2. Сразу после публикации ограничить доступ, иначе управлять колонкой сможет любой,

## 32. Громкость «прибавляется» после «далее» на тихом уровне (1–3)

**Симптом:** стоит громкость 2, листаешь треки голосом — с каждым «далее» музыка
становится громче, хотя команды громкости никто не давал.

**Почему так:** в Music Assistant (и в состоянии станции, которое он получает)
громкость всё это время остаётся **20 %** — навык её не трогает. Прибавляет сама
станция после собственной озвучки названия трека: на тихих уровнях её голос
звучит громче и она «возвращает» себе уровень выше заданного, а провайдер этого
изменения не видит.

**Что делать:** в `.env` включён `VOLUME_LOCK=1` (по умолчанию) — навык через
секунду после «далее»/«назад»/«паузы»/«продолжи» выставляет последний заданный
уровень заново. В логе это видно как:

```
alice: громкость возвращена к 2/10
```

Если строки нет — значит громкость ещё ни разу не задавали голосом: скажите
«громкость 2» один раз, дальше навык помнит уровень. Отключить защиту: `VOLUME_LOCK=0`.

**Если не помогло:** проверьте, не включена ли на станции адаптивная громкость
(«громкость по обстановке») — она меняет уровень независимо от навыка.

## 33. Сборка навыка падает: `Temporary failure in name resolution`

**Симптом:** `docker compose build` падает на шаге `pip install`:

```
NewConnectionError(... Failed to establish a new connection:
[Errno -3] Temporary failure in name resolution)
ERROR: No matching distribution found for fastapi==0.115.6
```

**Причина:** внутри сборочного контейнера не работает DNS. Обычно роутер отвечает
на DNS хосту, но **не отвечает контейнерам в bridge-сети** (частая история с
фильтрацией UDP/53 и IPv6). Проверить:

```bash
docker run --rm python:3.12-slim getent ahostsv4 pypi.org   # пусто → DNS нет
docker run --rm --network host python:3.12-slim getent ahostsv4 pypi.org  # работает
```

**Что делать:** собрать образ с сетью хоста и перезапустить контейнер:

```bash
cd /opt/alice-skill
DOCKER_BUILDKIT=0 docker build --network host -t alice-skill-alice-skill:latest .
docker compose up -d --force-recreate
docker exec alice-skill grep -c VOLUME_LOCK /app/app.py   # проверка, что код новый
```

Постоянное решение — прописать рабочий DNS демону Docker (`/etc/docker/daemon.json`):

```json
{ "dns": ["1.1.1.1", "8.8.8.8"] }
```

и `systemctl restart docker`.
